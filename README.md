# Forge

**AI-powered discipline and habit-building application** with adaptive daily
missions, cinematic Daily Transmissions, an event-driven mission lifecycle,
a fair progression/competition system, a social layer, and a real
authoritative Supabase backend behind it all.

Forge started as a fully offline, deterministic Flutter app — every system
ran against curated mock data with no backend required — and that mock-first
default still works with zero configuration. A real backend now exists
behind the same interfaces: Supabase/Postgres with RLS, SECURITY DEFINER
command functions, and Deno Edge Functions independently re-validate every
mission completion, XP award, achievement unlock, and competitive score
before any of it becomes confirmed.

> **Status: active development, pre-release.** This is not yet a published
> app. The backend is **locally runtime verified**, not staging- or
> production-verified — see [Project Status](#project-status),
> [Trust Boundaries](#trust-boundaries), and
> [docs/ROADMAP.md](docs/ROADMAP.md) for exactly what's implemented today.

---

## Overview

Every day, Forge selects one mission for the user from a curated catalog
using a deterministic rules engine, delivers it through a scripted
"Daily Transmission" from an in-universe AI character (The Watcher), tracks
the user's progress through an auditable, event-sourced lifecycle, and
turns completions into a locally-computed, clearly non-authoritative XP/
level/achievement preview.

Nothing here is generated by a live AI model yet. Nothing computed on the
client is ever *trusted* as a source of truth for anything competitive —
a real backend now independently recomputes and confirms it — but nothing
has been deployed anywhere beyond a local machine yet either. Both of
those are deliberate, current-phase constraints — see
[Trust Boundaries](#trust-boundaries).

## Core Features

- **Discipline Intelligence Engine** — a deterministic mission-selection
  pipeline (catalog → eligibility → safety policy → difficulty scaling →
  recovery handling → personalization scoring → selection) that always
  produces the same mission for the same inputs, with a human-readable
  explanation of *why* it picked what it picked.
- **Character & Daily Transmission system** — a full presentation flow
  (reveal → dialogue → mission reveal → accept) driven by hand-authored,
  deterministic mock scripts and local text-to-speech, built around
  reusable character-state/animation primitives.
- **Event-sourced mission lifecycle** — mission progress is never a single
  mutable status flag. Every action (view, accept, start, pause, resume,
  update progress, submit, complete, undo, reject, abandon) is an immutable
  event; current state is derived by replaying those events, which makes it
  auditable and safe to recompute at any time.
- **Ten reusable progress controls** — binary, counter, timer, checklist,
  percentage, quantity, reflection, reading, coding-session, and hydration
  missions each get a purpose-built, accessible control.
- **Progression system** — deterministic XP evaluation with documented
  caps and diminishing returns, a level ladder, behavior-earned cosmetic
  titles, and an achievement engine with locked/progressing/unlocked
  states. Local preview is instant; confirmed values come from the
  backend.
- **Fair competition** — seasons, weeks, a 6-tier league system, rookie
  placement/protection, a deterministic weekly competitive score kept
  entirely separate from XP, best-N-of-M season aggregation, and a
  Hall of Fame that never feeds back into current ranking.
- **Authoritative backend** — Supabase/Postgres with Row Level Security
  on every table, SECURITY DEFINER command functions, and Deno Edge
  Functions that independently re-validate and re-score every mission
  completion server-side. The client reconciles its local provisional
  state against confirmed results without ever overwriting a confirmed
  value with a local guess.
- **Social** — friends, friend requests, an activity feed, and
  visibility-gated public profiles (public/friends-only/private,
  friends-only by default).

## Architecture

Forge follows **Clean Architecture** on a **feature-first** folder layout:
every feature owns its own `domain/`, `data/`, and `presentation/` layers
under `lib/features/<feature>/`. Cross-cutting concerns (theming, routing,
storage, config) live under `lib/core/`; small stateless UI primitives
shared across features live under `lib/shared/`.

Domain layers are kept independent of Flutter and of each other's data/
presentation layers wherever the codebase's own comments call that out —
policies and engines are plain Dart, unit-testable with no widget
dependency. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the full
breakdown, including how the mission engine, character system, mission
lifecycle, and progression engine fit together, and where the client/server
trust boundary actually sits today.

## Environment Configuration

Forge reads configuration at **build/run time** via `--dart-define`, not
from a `.env` file (see [`.env.example`](.env.example) for the full,
documented list of values — that file is reference documentation only and
is not loaded automatically).

The default configuration requires nothing: running the app with no
`--dart-define` flags at all gives you `APP_ENV=mock`, which never touches
a network or a real credential.

```bash
# Default — mock mode, no configuration needed.
flutter run
```

```bash
# Live mode — only meaningful once a real Supabase project exists.
flutter run \
  --dart-define=APP_ENV=live \
  --dart-define=SUPABASE_URL=https://your-project.supabase.co \
  --dart-define=SUPABASE_ANON_KEY=your-anon-key
```

`SUPABASE_ANON_KEY` is a **public client key** by Supabase's own design —
access control is enforced server-side by Row Level Security, not by
keeping that key secret. It is still never checked into this repository
because it's project-specific, not because it's sensitive. A Supabase
**service-role** key is a real secret and must never appear in
`--dart-define`, source, or this repository under any circumstance.

## Running Tests

```bash
dart format --set-exit-if-changed .   # formatting check
flutter analyze                       # static analysis
flutter test                          # unit + widget + integration + golden
```

The suite currently has **740 tests** across unit, widget, integration, and
golden coverage, spanning the mission engine, the event-sourced mission
lifecycle, the character/transmission system, progression, competition, the
backend/sync/security layer, and social. **730 pass; the 10 golden-image
tests currently fail on non-Windows-baseline environments purely from font
rendering** (`google_fonts` falls back to a substitute font when the real
Inter `.ttf` isn't bundled for the test sandbox, producing a 0.04%–0.54%
pixel diff against the committed reference images) — **every functional,
logic, and behavioral test is green.** This is a known visual-test
infrastructure gap, not an application bug; see
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) and `dart_test.yaml` for the
`golden` tag used to isolate these:

```bash
flutter test --exclude-tags=golden   # everything else — the number that matters day to day
flutter test --tags=golden           # goldens only, on the OS the baselines were generated on
```

Golden images live under each feature's `test/**/golden/goldens/` and are
tracked in version control as the approved reference; `flutter test`
writes a sibling `failures/` directory with diff images only when a golden
comparison fails — that directory is gitignored and never meant to be
committed.

The backend (Supabase schema, RLS, and the `forge_*` command functions) has
its own independent verification harness — see
[supabase/tests/README.md](supabase/tests/README.md) and
`supabase/tests/verify_backend.sh` — which is **not** part of `flutter
test` and requires Docker.

## Security Model

- **No secrets are required to run or build this app in its default (mock)
  configuration.**
- The only client-side config value with any sensitivity nuance is the
  Supabase anon key, which is a public-by-design client key (see above).
- Session tokens and the onboarding-completion flag are persisted through
  the platform keystore (`flutter_secure_storage`), never in plain local
  storage.
- See [SECURITY.md](SECURITY.md) for vulnerability reporting and
  [Trust Boundaries](#trust-boundaries) for what the client is and isn't
  allowed to be authoritative about.

## Trust Boundaries

This is a load-bearing constraint across the mission, progression, and
competition systems, not an incidental detail — and it hasn't changed now
that a real backend exists, because the backend was built specifically to
enforce it:

- **The client is never authoritative for anything competitive or
  reward-bearing, even now.** XP, achievement unlocks, level-ups, and
  competitive scores computed on-device are explicitly and permanently
  marked `provisionalOnly` in their own data models. There is no client
  code path that writes a confirmed value directly — `confirmed_xp`,
  `season_results`, achievement rows, and league placement all live in
  Postgres, written only by SECURITY DEFINER functions the client cannot
  call directly, and RLS denies the client `INSERT`/`UPDATE` on every one
  of those tables (verified by `supabase/tests/003_no_client_authority_
  writes.sql`).
- Every mission completion is re-validated and re-scored server-side —
  the server's XP calculation is required to match the client's
  deterministic formula exactly (verified by
  `supabase/tests/010_reward_calculation_and_privacy.sql`), not because
  the two are allowed to differ, but so a formula bug is caught by a
  failing test rather than becoming an exploit.
- Week/season finalization (ranking, promotion/demotion, best-N-of-M
  aggregation) and daily mission assignment are also
  SECURITY DEFINER-only — not callable by an authenticated client at
  all, only by a trusted server-side invoker.
- **Current verification status: locally runtime verified, not staging-
  or production-verified.** All 24 migrations apply cleanly from zero
  against a real local Postgres, and all 14 SQL test files (RLS
  ownership, no-client-authority-writes, integrity/audit lockdown,
  duplicate prevention, command auth boundary, idempotency, reward
  calculation, week/season finalization, mission assignment, achievement
  canonical IDs, weekly grouping) pass every assertion. This has **not**
  been run against a deployed Supabase project, and no Edge Function has
  been deployed anywhere — see [docs/ROADMAP.md](docs/ROADMAP.md) Item 13.
- Every XP/level/achievement formula is versioned (`evaluationVersion`)
  so a stored local evaluation can always be traced back to the exact
  rules that produced it when the backend re-checks it.

## Known Development Constraints

These are current, deliberate scope boundaries — not oversights:

- No AI provider (OpenAI, Gemini, Claude, Ollama, or otherwise) is
  integrated. Character dialogue is entirely hand-authored, deterministic
  mock content.
- A real Postgres-backed persistence layer exists (Supabase), but it is
  **local-only so far** — no staging or production Supabase project has
  been created, and no Edge Function has been deployed anywhere. In mock
  mode (the default), the client still keeps everything in-memory per app
  session.
- No push notifications, no monetization.
- Only Android, Web, and Windows platform folders exist in this repository
  (no iOS/macOS/Linux scaffolding yet).
