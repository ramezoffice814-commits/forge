# Android Beta Signing Setup

Roadmap Item 22 ("Free Public Beta Launch"). Public APK update
continuity — installing beta build N+1 over N without uninstalling —
requires every release build to be signed with the **same** persistent
key. Debug signing (a different key per machine/CI run) cannot provide
this. **No signing key is generated by this document or by this
item.** This is the exact, one-time procedure for the human owner of
this project to create one.

## Secure CI signing path (selected, not yet run)

Since local builds remain blocked, a manual-dispatch-only GitHub
Actions workflow was added:
`.github/workflows/android_beta_signed_build.yml`. It never runs on a
`pull_request` or `push` — only when a human explicitly triggers it —
because it is the one workflow that touches real signing secrets. It
produces a **private** workflow artifact (this repository is private,
confirmed via `gh repo view`, so the artifact is visible only to
accounts with repository access) — never a GitHub Release, never a
public URL.

1. **Base64-encode the keystore, straight to your clipboard** — this

2. In GitHub: go to this repository → **Settings → Secrets and

3. Name: `CAN_ANDROID_KEYSTORE_BASE64`. Value: paste (Ctrl+V) the
   clipboard content from step 1. Click **Add secret**.
4. Repeat **New repository secret** three more times for
   `CAN_ANDROID_STORE_PASSWORD`, `CAN_ANDROID_KEY_PASSWORD` (your own
   known values, typed directly into GitHub's own secret field — never
   into this chat), and `CAN_ANDROID_KEY_ALIAS` (value: `can-beta`).
5. Once all four secrets exist, the workflow can be run manually from
   the **Actions** tab → "Android Beta Signed Build (manual)" → **Run
   workflow** → type `sign` in the confirmation field it asks for.
   **This has not been done yet** — running it is a separate, explicit
   step for you to take (or ask for) when ready; it was not triggered
   by this pass.

### What the workflow does (full detail in the workflow file itself)

Checks out the code, decodes the keystore into the runner's own temp
directory (never the repo working tree), writes a temporary
`android/key.properties` from the secrets (via `env:`, never inlined
into shell script text — the pattern GitHub itself recommends),
builds `flutter build apk --release`, verifies the result with
`apksigner verify --print-certs` and `keytool -list` (both filtered to
public fields only), checks the package name/version, generates a
SHA256 checksum, uploads the APK + checksum as a private artifact, and
explicitly deletes the temporary keystore/`key.properties` files
afterward (`if: always()`, so cleanup runs even on failure).

## Why this matters specifically for a public beta

Unlike the production-signing discussion in
[docs/RELEASE_CANDIDATE_2.md](RELEASE_CANDIDATE_2.md) (which was
about eventual Play Store submission), this key is needed **now**,
before the first beta APK is distributed — because the distribution
channel itself (a signed APK via GitHub Releases, not Play Store) has
no other mechanism to guarantee update continuity. Google Play would
otherwise handle key management (or even generate one via Play App
Signing); a self-distributed APK has no such safety net. **Losing this
key after the first beta release means every future update requires
every existing beta user to uninstall and reinstall from scratch,
losing their local Android Keystore-held session** (their server-side
account/data is unaffected — only the local session/preferences are
device-local, see [docs/RECOVERY.md](RECOVERY.md) "Local (on-device)
data").

## One-time setup (for the human owner to perform)

1. **Generate the keystore**, outside this repository entirely — a
   password manager's attached-file storage or a dedicated secrets
   vault, **never** inside `F:\365_day_chalange_app`, even in a
   gitignored path (a local accident — a misconfigured backup tool, a
   future `git add -f` — is one avoidable risk away). Recommended
   location:
   ```
   %USERPROFILE%\CAN-secrets\can-beta-release.jks
   ```
   Generate it with:
   ```
   keytool -genkey -v -keystore "%USERPROFILE%\CAN-secrets\can-beta-release.jks" -keyalg RSA -keysize 2048 -validity 10000 -alias can-beta-release
   ```
   (Following Android's own documented flow:
   https://developer.android.com/studio/publish/app-signing.)
2. **Choose a strong store password and key password** (can be the
   same value; two independent strong passwords is safer). **Never
   paste either into a chat session, a commit message, a log, or any
   file this repository tracks.**
3. **Copy `android/key.properties.example` to `android/key.properties`**
   (exact filename — already gitignored at both the repo root and
   `android/` level, confirmed this pass) and fill in the four real
   values (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`)
   using a plain text editor, locally, never through this assistant.
   Once present, `android/app/build.gradle.kts` automatically signs
   release builds with it — no other code change is required (this
   plumbing already exists, built in Roadmap Item 19, re-verified
   working this pass).
4. **Back the keystore file up somewhere durable and access-controlled**
   — not solely on one machine. A password manager's encrypted file
   attachment, or a dedicated secrets vault with its own backup policy,
   both work. **Losing this file without a backup permanently forecloses
   updating this specific beta APK lineage** — a new lineage would need
   a new package identity or a fresh install for every user, exactly
   the outcome this whole setup avoids.

## What happens once `key.properties` exists

Nothing further needs to change in this repository. The next
`flutter build apk --release` (or `appbundle`) run automatically
detects `android/key.properties`, validates all four required fields
are present (failing the build immediately and clearly if any is
missing — this fail-fast behavior is already implemented and tested,
see `android/app/build.gradle.kts`), and signs the release artifact
with the real key. CI does **not** need or use this file — every CI
build continues to fall back to debug-signing (no `key.properties`
exists in the CI environment, by design), so ordinary PR validation
never requires the human's private key. The real, human-signed
distributable APK is a **local, human-run build**, produced only when
actually preparing a beta release for distribution.

## What this document explicitly does not do

- It does not generate a keystore.
- It does not choose or invent a password.
- It does not print, log, or request any password value in this

- It does not commit any signing artifact.
- It does not distribute anything.
